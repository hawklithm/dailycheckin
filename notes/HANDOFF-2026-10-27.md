## 0. 一句话现状

**代理可用**：`trae2api` 暴露 OpenAI 兼容接口，能对话、能跑工具、能透出真实
token 用量（本轮新增）。

**但"原生 Trae 体验"不可达**，原因已彻底查清，**不是实现不足，是架构限制**：

> agent 能力（28 种 SSE 事件、结构化 `tool_call`、`thought`、子代理）
> 位于 **sidecar ↔ ai-server 之间的 aha IPC**，
> **不是 HTTP 接口**，外部进程无法接入。

### 2.2 鉴权链路（可用，本轮已验证无 scope 问题）

1. OAuth PKCE + ECDSA P-256 DeviceProof
   - `device_id` = `4333646823299987`
   - `machineId` = `56cb66e60ecd32141cfe256f4e5ff76e7f8d53bc99c6a93f8ef48b7cb0068524`
   - `user_id` = `3481484447459108`，region `CN`
2. 凭据解密自 `%APPDATA%\Trae CN\User\globalStorage\storage.json`
   （AES-128-CBC，头部 `[116,99,5,16,0,0]`）
3. 换 JWT：`POST {host}/api/v2/GetUserToken`，头 `X-Cloudide-Token`
4. 刷新：`POST /trae/api/v3/oauth/ExchangeToken`

**JWT 结构（本轮解码）**：

```
header : {"alg":"RS256","typ":"JWT"}
payload: data{ id, source:"refresh_token", source_id }, exp, iat
         ← 没有任何 scope / aud / role / entitlement claim
```

**结论：登录流程不产生额外权限，且与客户端发出的头完全一致
（`Authorization: Cloud-IDE-JWT` + `x-ide-token`）。不是登录问题。**

重建凭据（`trae2api/trae2api.json` 丢失时）：
```bash
python tests/rebuild_creds.py && python tests/add_device_key.py
```

### 2.8 错误码对照

| code | 含义 | 触发条件 |
|---|---|---|
| `2001` | `failed to get app config: record not found` | **旧卡点，已解**：根因是请求头，不是 `function` |
| `3003` | `all models failed` | 信封嵌套 `data{}` 时触发；字段必须在**顶层** |
| `4001` | param invalid，或 `config item is empty for config opt`（会打印**完整配置查找键**） | 参数缺失 / 配置不存在 |
| **`4011`** | rate limit | **已证：端点/function 级限制，非账号配额**（见 2.9） |
| `4000105` | `missing history count exceeded for session` | 同一 session_id 反复重建历史；**每次用新 session 即可避免** |
| `4023` | model unknown | V1 传未知模型名 |
| `404` | 路径错 | 注意 pay 类接口需要 `/trae` 前缀 |

### 2.9 ★ 4011 的真实含义（本轮定论）

同一秒、同一账号、同一 token、同一套头的对照实验：

```
/api/ide/v1/chat              -> 200 STREAM OK     ← 身份完全通过
/api/agent/v3/llm_utils_chat  -> 200 4011 限流
```

`llm_utils_chat` 按 function 区分两种情况：

| function | 响应 | 含义 |
|---|---|---|
| `agent` / `code` / `summary` | `no function config found` | 配置**不存在** |
| `solo_agent` / `builder` / `chat` | `4011` | 配置**存在**，但该端点不提供主对话 |

**结论：`4011` 是端点级限制。`llm_utils_chat` 是辅助工具端点
（名字即 `llm_utils`），本来就不负责主对话。**

### 2.10 配置查找键（服务端主动泄露）

`create_agent_task` 返回 `config item is empty for config opt:`

```json
{"AppId":"6eefa01c-...","Function":"solo_agent",
 "ConfigName":"deepseek-v4.1-flash","VersionCode":20260212,
 "ModeType":0,"AgentType":"solo_agent","IsCustomModel":false,
 "Account":{...},"Provider":"","RequireMultimodel":false}
```

这是当年 `2001` 死活猜不到的**完整查找元组**，现已确认。

### 2.11 账号状态（已解密，非瓶颈）

`storage.json` 的 `iCubeServerData://icube.cloudide` 是**明文 JSON**（不是加密的）：

```json
{"entitlementInfo":{"identityStr":"Free","identity":0,
  "enableSoloBuilder":true,"enableSoloCoder":true,
  "detail":{"can_gen_solo_code":false,"permission":0}}}
```

**重要更正**：`can_gen_solo_code: false` 指的是「SOLO 生成代码」子功能，
**不是 agent 对话不可用**。真实客户端 **90 次成功出字**，
额度/配额/升级信号 **0 次**，`restrictedModelKeys: []`。

**账号授权不是瓶颈。**

### 2.12 ⚠️ 重要陷阱：providers 不是第一方额度池

`providers` 返回的模型（`deepseek-v4-flash`、`doubao-seed-2-1-*`、
`glm-5.3`、`kimi-k3` 等）是 **BYO-key `billing_mode:"paygo"` 池**，
不是 Trae 第一方额度。**不要拿这些名字去解锁 V1 chat**（必然 `4023`）。

## 4. 已经试过并**确认失败**的路（别再走）

| 方案 | 结果 | 证据 |
|---|---|---|
| mitmproxy 系统代理抓 sidecar | ❌ sidecar 不走系统代理 | 76 请求中目标域名 0 次 |
| `ICUBE_PROXY_HOST/PORT` + `--preserve-env` | ❌ 无效 | sidecar 用 TTNet/cronet |
| 连 40005 端口 | ❌ 没监听 | `meta.json` 是历史声明 |
| 连 mojo 命名管道 | ❌ 单实例不可附加 | `os.open` EINVAL |
| `ReadProcessMemory` 读内存 | ❌ 拿不到完整 body | `memscan_sidecar.py` |
| `netsh trace` | ❌ 需提权且 TLS 加密 | — |
| 解 `.alaudalog` | ❌ 加密 | magic `AalG` |
| 直读 sidecar `database.db` | ❌ **SQLCipher 加密** | 头 16 字节随机；DLL 含 `sqlcipher`×165 |
| 枚举 `function` 解 `2001` | ❌ 20 个键全空 | 根因是请求头 |
| 枚举 `env` 解 `2001` | ❌ 10 env × 5 位置全空 | 同上 |
| 换 app id B | ❌ 4 种组合仍 `4011` | `850edec7-…` 无差别 |
| 补身份头 16 种组合 | ❌ 全 `4011` | 与 V1 成功请求逐字段 diff |
| 改 body 形状 | ❌ 最小 body 也 `4011` | 限流在解析前 |
| 顶层补 `ChatArgs` 全部能力字段 | ❌ `tool_calls` 恒 null | 该端点无结构化工具通道 |
| 找 `api/v1/chat/*` 远端路由 | ❌ **150 组合全 404** | 3 方法 × 10 前缀 × 5 路径 |
| 找 `api/agent/v3/*` 当主对话用 | ❌ `4011` | 它是工具端点，非主对话 |

**核心结论**：agent 能力在 **aha IPC（非 HTTP）**，外部进程不可接入。

## 5. 下一步（三选一，需人决策）

### 方案 A：接入 aha IPC（技术上有理论可能，风险高）

需要伪造 `@aha-kit/rpc` 客户端 + 加入运行时 UUID socket。
**障碍**：socket 名是运行时生成的 UUID；`electron.ahaIpc` 依赖 Electron
主进程句柄；Trae 无 LISTEN 端口（已验证）；mojo 管道不可附加。
**不保证能成。**

### 方案 B：驱动本机真实客户端（最可靠）★ 推荐

## 7. 给接手 agent 的硬约束

1. **不要再找"真实 HTTP 接口"**——已穷举证明不存在
   （150 组合全 404）。agent 能力在 aha IPC。
2. **不要再怀疑账号授权 / 登录流程 / 域名 / appId**——全部已验证正常
   （Free 账号 90 次成功出字；JWT 无 scope；boot-config 域名与现用一致）。
3. **不要再枚举 `function` / `env` / app id / 请求头**——全部证否，见第 4 节。
4. **`v1/chat` 必须用 legacy 设备头**，不要用 `_modern_headers()`
   （会 500 / 4001 / 2001）。
5. **`api/ide/v1/chat` 从顶层读字段**；把 chat 字段嵌进 `data{}` 会得到
   `3003 all models failed`。
6. **不要动 `_headers()` 现有字段语义**（V1 依赖它）。新增用途请新建方法。
7. **不要再用 `providers` 的模型名**去试 V1（BYO-key，必 `4023`）。
8. **session_id 每次要用新的**，否则触发 `4000105 missing history count exceeded`。
9. **真相在明文日志里**：`%APPDATA%\Trae CN\logs\**\*.log`
   （`renderer.log` / `completion.log` / `Modular\cue-server_*_stdout.log`）。
   只有 `.alaudalog` 是加密的。
10. **静态反编译有效**：Rust 二进制的 serde 字段名是明文连写的，
    配合 `struct X with N elements` 可还原权威 schema。
