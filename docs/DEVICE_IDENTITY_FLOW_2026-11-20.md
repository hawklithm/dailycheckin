# 设备注册、登录身份与签到设备处理

日期：2026-11-20。依据当前工作区源码与本机 Trae CN 3.4.20 的字段取证。
本轮为代码路径梳理，未发起注册、激活、登录或签到请求。

## 字段来源

| 层次 | 主要信息 | 来源与用途 |
|---|---|---|
| 真实硬件 | SMBIOS UUID、磁盘序列号、MAC、型号、制造商、CPU、OS | `Hardware.read()` 读取；注册使用其中的硬件信息，OAuth 使用相应设备描述 |
| 本地登录配置 | machine ID、P-256 密钥对 | `IdentityStore.load()` 在无已有配置时生成；有旧独立凭据时可能迁移，之后持久化复用 |
| 远端注册身份 | device ID、install ID、region | 注册服务响应；客户端校验非零十进制 ID，随后确认激活 |
| 账号授权 | user ID、token、refresh token | 浏览器授权、ExchangeToken 与 GetUserInfo；和本次登录使用的设备上下文一同保存 |
| 签到身份 | token、`x-device-id`、地区及客户端元数据 | 从选定的原生身份或独立凭据构造；不在签到过程中生成或注册设备 |

machine ID、公钥、硬件 UUID 与远端 device ID 是不同字段。修改一个字段不能作为
其他字段已改变或服务端已认可一台新设备的证明。

## 独立登录路径

```text
明确选择凭据文件
  -> IdentityStore：读取/初始化该路径的持久化本地登录配置
  -> prepare_device：读取真实硬件
  -> 无注册缓存时请求注册，接收远端 device ID / install ID
  -> 确认激活并保存配置
  -> 使用同一设备上下文完成浏览器授权和 ExchangeToken
  -> GetUserInfo 确认 user ID
  -> 原子保存账号凭据与登录所用的设备上下文
  -> checkin --creds：使用保存的 token 与 device ID 查询签到状态
```

对应源码：`login_identity.py` 的 `IdentityStore`，`login.py` 的
`prepare_device()`、`_device_info()`、`_login()`，以及
`aha_registration.py` 的 `register()` / `activate()`。

注册请求构造函数不接收账号 ID，本地 machine ID 和登录公钥也没有作为参数传入
该注册请求。注册发生在账号授权之前。因此，不能从“不同账号配置有不同 machine ID
或密钥”推导出“注册服务必然给出不同设备 ID”。服务端对同一硬件的去重算法尚未确认。

已注册配置会复用远端 ID；硬件 UUID 与保存值不一致时停止。
现有真实硬件注册成功的历史证据，也不能替代新独立登录到签到的完整验收。

## 原生身份路径

`checkin --native` 从原生存储读取当前账号 token；从最新会话日志核对远端设备解析结果，
要求与原生 OAuth 设备记录匹配。每次请求前重新核对账号、token、设备、地区和会话。
此路径没有按账号生成新设备的步骤。换账号本身也不意味着设备改变。

## 签到接口怎样使用设备

`checkin.py` 的请求头包含账号 token 与 `x-device-id`。
已审查实现的请求体为 `{"req_source":1}`，不在其中提交整套硬件信息。
客户端可见的状态判断是：

- `checked_in=true`：账号今日已签到。
- `checked_in=false, did_checked_in=true`：设备限制；原生界面显示设备今日已签到。
- `enable=true` 且两个签到标记均未阻止时，才进入领取流程。

以上是客户端行为证据，不能证明服务端只依赖一个请求头判定设备；
服务端如何结合设备注册、登录上下文或其他信号尚未还原。
详细原生文案与源码证据见 `TRAE_CN_CHECKIN_FIELD_SEMANTICS_2026-11-20.md`。

## 账号隔离的现状与合理边界

当前 `IdentityStore` 按所选凭据文件的目录和文件主名确定 `.device.secret` 路径，
并非按服务端 user ID 自动分配。首次创建不同配置时可生成不同的本地 machine ID 和密钥；
它们仍读取本机真实硬件，远端设备 ID 是否不同由注册服务决定。
同目录下同主名、不同扩展名的凭据文件还会共享同一个设备配置路径。

正常的账号管理应显式记录账号与真实注册设备的配对，保留各自凭据，并在重新登录时
核对实际返回的 user ID。当前实现尚无“预期账号 ID”绑定校验，不应将文件名视为账号证明。
也不应把一个已有登录 token 与另一个任意设备 ID 拼接后当作已验证登录上下文。

`device_identity.py` 已有按账号保存的离线合成 UUID 候选，但明确标记为未注册；
它不属于生产签到链路，也不能证明服务端接受该设备。
不同设备夹具的生成、幂等和隔离可以在本地 mock 或明确授权的测试端点中验证。
本梳理不把合成硬件指纹接入生产签到，不实现规避设备签到日限的功能。
