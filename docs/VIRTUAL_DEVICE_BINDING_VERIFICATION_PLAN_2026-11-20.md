## 1. 要回答的问题

提交一套虚拟设备信息，不等于已证明服务端认可了一台独立物理设备。
本方案将以下结论分别验证，不以某一阶段成功替代后续阶段：

| 层次 | 要验证的结论 | 所需证据 |
|---|---|---|
| L1 输入构造 | 合成设备描述可以稳定构造并被本地校验 | 固定夹具、字段类型、重复加载一致性 |
| L2 注册与激活 | 测试注册服务接受该描述并返回可用注册身份 | 注册/激活的业务结果、设备记录关联 |
| L3 账号授权 | 测试账号可通过正式授权使用该设备上下文 | 授权交换、实际 user ID、服务端会话与设备关联 |
| L4 可信绑定 | 设备信息无法未经认证地脱离登录会话替换 | 服务端最终设备身份、错配处理结果 |
| L5 日限一致性 | 同一设备的多安装或多账号不产生超出规则的奖励 | 权威设备键、业务日期、额度记录、测试奖励流水 |

L2/L3 成功不自动代表漏洞。不同合法设备具有不同额度也不代表绕过。
只有在服务方明确的设备定义与业务规则下，出现不应允许的身份替换或超额记账，才能确认缺陷。

## 2. 现有代码事实

- `device_identity.py` 只生成离线合成 UUID 候选，不进行注册或账号绑定。
- `aha_registration.py::registration_request()` 提交设备硬件描述；不提交账号 token、
  user ID、本地 machine ID 或设备公钥。
- 注册响应提供 device ID/install ID，激活请求引用它们并再次携带部分设备输入。
- `login.py::exchange_auth_code()` 使用 AuthCode、PKCE verifier 和 DeviceInfo 换取 token；
  DeviceInfo 含远端设备 ID、machine ID、公钥及设备描述。初次交换没有显式 DeviceProof。
- `auth.py::exchange_refresh_token()` 使用 DeviceProof；它与初次授权码交换应分开分析。
- `checkin.py` 使用 token 和 `x-device-id`；现有客户端会在设备限制状态下提前返回。
- 原生界面明确区分账号已签到与设备已签到，见字段语义取证文档。

上述事实只来自客户端代码。服务端的注册去重、会话绑定、公钥选择及额度键尚未确认。

## 3. 验证环境与前置参数

提供三种结果来源，报告必须显式标注：

1. `offline_fixture`：只构造/检查夹具，不联网。
2. `local_mock`：本地模拟注册、授权关联与测试记账，验证实验方法和报告；不能证明真实服务行为。
3. `provider_test`：服务方明确授权的测试注册、OAuth、签到与测试记账环境；允许使用真实授权流程，
   但账号须由服务方指定为测试账号，奖励不进入实际权益。

远端阶段开始前需明确：

- 注册、激活、授权、token 交换、用户信息、状态与领取端点及协议。
- 测试 appId/clientId、回调地址、测试账号 A/B 和允许的账号授权方式。
- “设备”是物理机器、安装实例、密钥身份还是其他对象；每日次数按哪个业务时区定义。
- 测试设备的可信登记方法、允许的夹具输入、各接口是否共享设备身份空间。
- 后端审计记录/只读查询途径，以及测试奖励隔离或回滚机制。
- 请求预算、测试时间窗口及停止条件。

当前这些远端参数未齐备，`provider_test` 阶段为 **not_run**。
不自动使用仓库现有生产地址、生产 appId、原生账号缓存或已有生产 token 作为默认参数。
既有 `SANDBOX_DEVICE_LAB_DESIGN_2026-11-20.md` 的 v1 协议仅包含注册/激活；
其 capability 握手不能授权 OAuth 或奖励测试。新增适配需要单独的明确契约。

## 4. 夹具与身份模型

使用有限、固定、持久化的测试夹具，不每次随机生成所有字段：

| 对象 | 表示内容 | 用途 |
|---|---|---|
| H1 | 第一台模拟物理设备的稳定合成描述 | 重注册、重装、跨账号的共同对照 |
| H1-display | 按服务方定义仅改变非身份描述的 H1 变体 | 检查展示字段是否错误改变额度身份；字段分类须事先确认 |
| H2 | 第二台独立模拟物理设备的合成描述 | 不同设备的正常对照 |
| I1/I2 | H1 上两个安装/登录配置，分别持有本地 machine ID 和密钥 | 区分物理设备与安装生命周期 |
| A/B | 两个指定测试账号 | 区分账号日限与设备日限 |
| D1/D1b/D2 | 注册服务实际返回的设备记录别名 | 不在本地预先制造远端注册 ID |

夹具 manifest 保存 synthetic 标记、版本和实验内关联关系。
manifest 不是发给远端的任意扩展字段；请求 adapter 只发送契约允许的字段。
不改写操作系统硬件标识，不修改原生客户端存储，不读取真实硬件作为合成夹具。

重要控制：当前生产注册协议不提交 I1/I2 的 machine ID 或公钥。
因此，对 H1 新建 I2 后的注册请求，本质上仍是相同硬件输入的再次注册，
只可能有时间等请求元数据差异。不能把远端 ID 的变化归因于根本没有发送的本地字段。

## 5. 阶段 A：离线准备

检查夹具结构、持久化一致性、身份字段与展示字段的分组、凭据路径隔离和端点配置。
默认 dry-run，网络调用次数严格为零。

产物是实验清单、单变量变化表和待发送请求类别，不输出 token、私钥、完整设备指纹或可直接发送的生产报文。
本轮只写方案，不开展此阶段。

## 6. 阶段 B：注册与设备归并

| 用例 | 输入关系 | 要记录的事实 | 结论边界 |
|---|---|---|---|
| R1 | H1/I1 首次注册并确认激活 | 注册结果、激活结果、返回身份别名 | 接受客户端声明，不等于硬件真实性已获证明 |
| R2 | 重放 H1 的注册输入 | 返回 ID 是否相同；后端规范化设备键是否相同 | ID 不同本身不是漏洞 |
| R3 | H1/I2；硬件描述保持不变 | 新安装是否仍关联 H1 的额度身份 | 若规则按安装计数，额度变化可能正常 |
| R4 | H2 注册并确认激活 | 是否作为独立设备处理 | 正常独立设备对照 |
| R5，可选 | H1-display | 展示变化是否改变设备归并 | 按确认的字段契约解释，不凭名称猜测字段权重 |

如果服务端不提供规范化设备键，只能记录外部可见 ID 的关系；不能宣称已还原物理设备去重算法。
注册超时或结果不明时不重试，不为该结果继续激活。

## 7. 阶段 C：账号授权与绑定

按服务方正式测试 OAuth 流程，让 A 使用 D1、B 使用 D1b 完成授权。
每轮使用新的授权码/PKCE 上下文，设备配置在整个流程中保持一致。
不将已有账号 token 与另一个设备 ID 拼装成“绑定成功”的证明。

逐项验证：

1. 实际 GetUserInfo 返回账号是否等于本用例指定的 A 或 B；不匹配立即停止。
2. 授权阶段与兑换阶段的设备信息是否一致，服务端是否记录一致性判断。
3. 会话是否关联到正确设备记录、公钥，以及哪个规范化设备身份。
4. token/refresh token 的设备约束是否来自可信服务端会话记录。

只拿到 token 或 GetUserInfo 成功，只能证明账号授权成功。
服务端没有设备关联证据时，绑定结论记为 `binding_unverified`。
初次授权码交换与 refresh token 设备证明分开记录；核心实验不刷新或轮换既有生产 token。

## 8. 阶段 D：设备声明是否可信

以测试会话为固定对照，检查以下情况：正常配对、缺少设备声明、未登记设备声明、
与会话不同的测试设备声明。每次只改变一个条件。

优先使用服务方提供的只读设备验证/状态接口，观察：

- 请求声明的设备；会话登记的设备；服务端最终选定的设备。
- 是否拒绝不一致声明，或按契约从会话恢复可信设备。
- 正常多设备授权是否需要额外认证，而非无条件采用本次请求声明。

接受错配并不自动等于漏洞：需要结合服务方的多设备会话规则。
只读状态结果也不能证明写入端采用相同校验。没有后端证据时，不将此阶段写为“服务端无绑定”。

## 9. 阶段 E：日限与测试记账

本阶段仅在明确隔离真实奖励的 `local_mock` 或 `provider_test` 中运行。

先确认测试业务日内 H1 尚无测试奖励记录，使用 A/D1 建立一次正常领取基线。
随后使用同一 H1 的 B/D1b 会话验证跨账号、跨安装的设备日限。

这里需要区分客户端 gate 与服务端校验：实验 adapter 在用例明确要求验证服务端拒绝时，
允许记录状态后提交一次预期被拒绝的测试领取；不能直接复用会提前跳过的生产 checkin()
并将“未发送请求”报告成服务端通过验证。此能力仅属于测试契约，不修改生产签到默认行为。

结合阶段 D，最多选择一个错配身份用例验证写入端的一致性。
不穷举设备身份、不批量注册，不开展并发或跨日竞态；它们需要单独的实验与预算。

判定必须同时核对：

- 同一个权威设备身份、同一业务日期、同一限额规则。
- 两个账号及其授权会话均正确，未混入历史奖励或其他活动奖励。
- 请求是否真正到达领取端，服务端选定了哪个设备和额度键。
- 测试奖励流水是否新增、是否最终有效；是否出现超出规则的有效奖励。

HTTP 200、业务 code=0、注册 ID 不同、状态字段变化，以及 mock 按预设规则成功，
均不能单独证明真实设备日限被绕过。

## 10. 请求预算与停止条件

未来执行器必须先编译本次选中用例的请求清单，再执行；超出预算的可选用例不运行。

- 单次实验程序化 HTTP 尝试硬上限：32 次，包含 capability、注册、激活、OAuth 交换、
  用户信息、状态、领取及远端只读审计查询；失败和超时也计入。
- 领取尝试硬上限：3 次，分别供正常基线、H1 跨账号对照、一个可选错配写入用例。
- 用户参与的浏览器授权会话最多 3 次；浏览器自身资源请求另行按服务方配额管理，
  不将“32 次程序化调用”冒充全部网络流量上限。
- 单线程、无自动重试。领取超时后不补发，仅按预留预算读取权威状态/流水。
- 结果不明、账号改变、注册身份改变、奖励隔离失效、预算耗尽、非预期目标或重定向时停止。
- 确认出现非预期有效奖励后即停止，不通过更多领取重复扩大影响。

## 11. 证据与报告

报告至少记录 experiment_id、来源、时间、用例、夹具版本、字段差异类别、请求计数、
阶段结果、脱敏账号/设备别名、服务端请求关联号、规范化设备关系和测试流水结论。
账号及设备别名映射仅保存在受限实验上下文，不进入公开报告。

不保存原始 token、refresh token、AuthCode、PKCE verifier、私钥、完整请求头或原始网络日志。
服务端只读记录也按同样规则脱敏。

结论使用以下分类：

- `accepted_synthetic_registration`：测试服务接受了合成注册输入。
- `account_authorized`：指定测试账号完成授权。
- `binding_unverified` / `binding_enforced` / `binding_gap_observed`：分别表示绑定未知、
  对选定用例有效、观察到违反既定绑定规则的结果。
- `quota_enforced` / `quota_bypass_confirmed` / `inconclusive`：只在设备定义、业务日、
  规则及最终测试奖励流水均可核对时判断。
- `not_run`：缺少契约、参数、环境或未获本次执行指令。

本文件当前所有阶段均为 **not_run**。

## 12. 当前已知限制

如果注册服务仅接收客户端自报字段，没有可信设备证明，客户端源码不能证明该记录代表
独一无二的物理硬件。应由服务方明确其信任模型，再区分产品设计限制、部署配置问题与实现漏洞。

本方案不改变现有生产路径，也不将合成注册通过写成生产账号绑定或签到绕过已获验证。
